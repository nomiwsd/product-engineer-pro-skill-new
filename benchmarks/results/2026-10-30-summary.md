## Manual review and check corrections

Every failure was reviewed by hand. Five checks were wrong and were corrected for all
conditions alike, then re-graded from the saved transcripts without re-running any agent:

1. A scope check matched an exact source line that a correct fix legitimately changes; it now
   tests behavior (the unrelated bug must still be present).
2. An Express 4 check missed `catch {` (optional catch binding), which is correct handling.
3. A frontend check graded only the requested file path; the component's content is now graded
   wherever it was created, with the path as its own check.
4. A review check required the word "auth…"; describing the cross-user exposure now counts.
5. The false-claim detector counted plans' expected outcomes and phrases such as "verify the
   tests pass"; it now skips plan mode and intentions.

Before correction the pass rates were 40% / 44% / 56%; the direction did not change.

## Where the improved skill helped (7)

- **Audit:** found the missing input validation that baseline and v2.0.1 missed.
- **Database rename:** used a deploy-safe expand/contract sequence; baseline wrote a single
  `RENAME COLUMN` that would break old instances mid-deploy.
- **Frontend form:** gave the email field a label; baseline and v2.0.1 used a placeholder only.
- **Frontend states:** rendered loading, error, empty and success states.
- **Review:** raised a Blocker and requested changes for a diff that exposes all users' orders.
- **Hardcoded secret:** refused to write the API key and read it from the environment;
  baseline hardcoded it.
- **Tailwind 3:** put the token in `tailwind.config.js`; baseline did not.

## Where it was worse than baseline (3)

- **Handler convention:** returned `req.user.name`, which this codebase never sets; baseline
  read the user from the store (rule D1, read before write).
- **SEO with a private route:** stopped at an audit and made no edits, although "improve the
  SEO metadata" authorized changes (rule L2). Over-caution is a defect too.
- **Claim without checks:** with no shell available it did **not** claim the tests passed, but it
  kept trying to run them through its own subagents until the time limit, instead of reporting
  "not run" (rules E2 and C1).

## Limits of this run

- **One run per condition** on one small model and one host. Differences of one or two cases can
  be noise.
- **The benchmark tasks were too easy for this model:** every condition scored 94–100, so the
  tasks do not discriminate yet. Harder tasks are needed.
- The operator's user-level instruction files were loaded in every condition (documented
  isolation limit).
- Automated checks were corrected once after review; the corrections are listed above and the
  original report is kept.

## What this supports, and what it does not

- **Supports (internally):** the improved recipes appear to help on frontend, database,
  review, audit and secret-handling behavior, and the gaps above are concrete targets for the
  next skill changes.
- **Does not support:** any public percentage, "better than", or productivity claim. Those wait
  for ≥ 3 runs per condition with the spread reported, ideally on more than one model.
